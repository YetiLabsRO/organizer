# Data migration: legacy `organize_*` → current `tasks_*`

Production historically ran the original 2017 `organize` Django app. The current code uses the
`tasks` app, whose schema is nearly identical — the only addition is `TaskItem.for_today` (and a
nullable `completed_date`). Users are still `auth.User`. This makes the migration a straight
table-by-table copy.

The `migrate_legacy` management command
([`tasks/management/commands/migrate_legacy.py`](../tasks/management/commands/migrate_legacy.py))
automates it. It has been tested end-to-end against a real production dump (14,517 tasks, 30,755
tag links, 27 tags, the admin user and its API token).

## What it does

1. Restores **only** the legacy `organize_*` tables (definition + data) from the dump into the
   target database (their names don't collide with `tasks_*`).
2. Restores identity data (`auth_group`, `auth_user`, `auth_user_groups`, `authtoken_token`) into
   the freshly-migrated auth tables.
3. Copies each `organize_*` table into its `tasks_*` counterpart with an explicit column mapping
   (`for_today` defaults to `false`). FK checks are bypassed for the copy via
   `session_replication_role = replica` (needs a superuser role), so insertion order and the
   `parent_task` self-FK don't matter.
4. Re-syncs every copied table's id sequence to `max(id)`.
5. Drops the temporary `organize_*` tables.

### Intentionally **not** migrated

`auth_permission`, per-user/per-group permissions, `django_content_type`, `django_admin_log`, and
`django_migrations` are skipped — they're regenerated by `migrate` and their ids do not line up
across the two schemas. Re-grant any per-user permissions in the admin afterwards. (In the tested
dump the only user is a superuser, so this was a no-op.)

## Prerequisites

- PostgreSQL client tools on PATH (`pg_restore`, `psql`).
- The production dump in **custom format** (`pg_dump -Fc`), e.g. `organizer.dump`.
- A target database **with the current schema applied but no task data yet**.
- The target DB role should be a superuser (required for the FK-bypass during copy).

## Runbook

Always migrate into a **copy**, never directly over production until you've verified a dry run.

```bash
# 1. Create a fresh target database and apply the current schema.
createdb -h 127.0.0.1 -U <user> organizer_new
uv run python manage.py migrate            # against organizer_new (set DB_NAME=organizer_new in .env)

# 2. Run the migration.
uv run python manage.py migrate_legacy /path/to/organizer.dump

# 3. Verify (see below), then point the app at organizer_new.
```

The command reads its connection from Django's configured `default` database, so select the target
by pointing `DATABASES` at it (set `DB_NAME` in `.env`, or inject `DB_*` env vars for a one-off run).

### Flags

- `--force` — proceed even if `tasks_taskitem` already has rows (otherwise the command refuses to
  import into a non-empty schema).
- `--skip-auth` — don't import users/groups/tokens (use when the target already has the users; the
  copied `owner_id`/`user_id` values must still match those users' ids).
- `--keep-temp` — keep the restored `organize_*` tables instead of dropping them (useful for
  debugging a run).

## Verification

```sql
-- Row counts should match the source dump.
SELECT count(*) FROM tasks_taskitem;        -- e.g. 14517
SELECT count(*) FROM tasks_taskitem_tags;   -- e.g. 30755

-- No orphaned tag links.
SELECT count(*) FROM tasks_taskitem_tags tt
  LEFT JOIN tasks_taskitem t ON tt.taskitem_id = t.id
  LEFT JOIN tasks_tag g ON tt.tag_id = g.id
  WHERE t.id IS NULL OR g.id IS NULL;        -- 0

-- Sequence is past the max id (next insert won't collide).
SELECT max(id), nextval(pg_get_serial_sequence('tasks_taskitem','id')) FROM tasks_taskitem;
```

Then smoke-test the API with an imported token:

```bash
uv run python manage.py runserver
curl -s -H "Authorization: Token <key from authtoken_token>" http://127.0.0.1:8000/api/task/ | head
```

## Rollback

The command does not modify production unless you point it there. To roll back a bad run, drop and
recreate the target database and start over:

```bash
dropdb organizer_new && createdb organizer_new
```
